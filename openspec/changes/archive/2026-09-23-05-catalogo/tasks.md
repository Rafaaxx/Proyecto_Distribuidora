> **Modo TDD estricto.** Dentro de cada grupo se escribe primero la prueba que falla (RED), después el código mínimo que la pasa (GREEN), después se triangula con al menos un segundo caso (camino feliz + un borde o error) y recién entonces se refactoriza, con las pruebas en verde después de cada paso. Antes de tocar un archivo que ya existe se corre su suite y se anota la línea base; una falla previa se reporta, no se arregla. Toda prueba de un invariante o regla lo cita por ID en su nombre o docstring (CAT-03, INV-18, CAT-08, …).
>
> **Gobernanza.** Dominio MEDIO (lógica de negocio de maestros): se implementa por grupos con punto de control al final de cada uno. Ninguna tarea se implementa sin la aprobación humana de esta proposal (`CLAUDE.md` §6 paso 4). Las tareas **[BLOQUEADA]** esperan la decisión del grupo 0. Las tareas **[ALTA]** tocan contrato de API o permisos de base: se describe el cambio y se espera confirmación antes de escribirlo.
>
> Orden: bloqueantes → línea base y límites → migración → modelos → dominio puro → fixtures compartidos CAT-08 → repositorio → servicio → handlers → consultas → API → frontend → pruebas de integración y concurrencia → deuda nominada → verificación.
